# PR review threads — live-PR findings

Recorded answers to the empirically-verified-facts block cited by
`scripts/lib/prt/gh.sh:13-21`, and to the V1-V7 spike questions from the Phase 2 plan. Each row
is a question that can only be answered by observing a real PR/merge-queue run against GitHub —
not by reading the code or the docs. This file is the scaffold; **do not fill in an answer
without having actually run the spike.** Rows stay `PENDING` until then.

V1 is answered by Phase 2 Task 4 (requires `merge_group:` wired into a real merge queue — see
Task 3). V2-V7 are answered by Phase 2 Task 5, run against a `.github` scratch PR once
`continue-on-error: true` is removed from `pr-review.yml`. **V6 is not cleanly answered** — the
spike hit a separate, reproducible silent-failure defect before it could observe a bot-resolve;
see the V6 row for what was actually found.

| V2 | Does `vars.PR_REVIEW_THREADS_MODE` resolve inside a *called* reusable workflow, and against which repo (caller's or callee's)? | **Caller's repo** (kure/launcher), not the callee (`.github`) that defines the workflow file — this is a documented GitHub Actions property, not directly observable from inside `.github`'s own dogfood PR (it calls itself, so caller==callee there). Consequence: an incident-mode repo-level override must be set on the affected consumer, not on `.github`. | 2026-08-18 | docs.github.com/en/actions/reference/workflows-and-actions/reusing-workflow-configurations: "When a reusable workflow is triggered by a caller workflow, the `github` context is always associated with the caller workflow" — `vars`/`secrets` resolution follows the same caller-bound job execution context (same reason `secrets: inherit` passes the caller's secrets). | V3 | Does an outdated-but-unresolved review thread still block merge? | **Yes.** A thread whose anchored line was pushed past by an unrelated content shift stayed `isOutdated: false` (GitHub's own diff-position tracking re-anchored it to the new line automatically) but remained gating regardless — `mergeStateStatus` stayed `BLOCKED` throughout. | V4 | Does a review thread anchored on a since-deleted file still block merge? | **Yes, and worse than expected.** Deleting the file made both threads `isOutdated: true, line: null` and `mergeStateStatus` stayed `BLOCKED` (expected). But because the file was added-then-deleted entirely within the PR's own commits, the diff against the merge-base netted to **empty** — and the script exits at `pr-review-threads.sh:130-134` ("No diff, nothing to review", `exit 0`) *before* the absence-reconciliation loop that would ever mark/auto-resolve a stale thread runs. Any PR whose net diff is empty (for any reason, not just this scenario) can never auto-resolve an existing gating thread — it's stuck until a future push produces a non-empty diff. Not fixed here; worth a follow-up issue. | 2026-08-18 | go-kure/.github#58, commit `b9676ad` (file deleted).
